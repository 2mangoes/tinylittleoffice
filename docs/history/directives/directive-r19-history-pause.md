# R19-history-pause: the address follows the document when the typing stops, not between words

**Paul, 2026-10-12**, asked whether the browser's history records every change of the address, and chose this: *"Do the first"*, of writing the address only after a pause in typing rather than on every edit. What stands today (`src/kit/core/shell.ts`): a keystroke stages the document and starts a timer; when typing pauses for `PAUSE` (150 ms) `flushLink` writes the document into the address with `history.replaceState`, and the same flush runs at once before anything reads the address (the window's blur, the focus leaving the words, the page hidden or left, Share, every copy, Display, print, the exports, a short link, the keep, the password, the title). So the Back stack has one entry per document; but a browser whose history records each replaced address (Chrome does) holds a state of the document at every gap between words, and its sync carries them. The mechanism is right; its pause is too short for what it protects.

## The design

- **The pause is a pause in typing, not a gap between keys.** `PAUSE` becomes two seconds, with the comment saying why: the address is what the browser's history and sync record, so it is written when the person stops, and at once whenever anything reads it or the page is hidden or left (the flushes that stand). Nothing else about the mechanism changes: one timer a burst, `flushLink` the one writer, `currentHash` in `kit/core/route.ts` flushing for a reader outside the shell.
- **Nothing is lost by the longer pause.** The flushes on `pagehide`, `visibilitychange`, the window's `blur` and `focusout` are what guard a document under Private against the tab closing or the phone switching apps; check each still runs and add the one that is missing if any (a phone's Home button is `visibilitychange` then `pagehide`; a desktop's close is `pagehide`). The library's keep (`keepSoon`, under Save in browser) follows the same flush, so a kept document is at most one pause behind, and never behind when the page is hidden.
- **Tests read the address through the flush, never by waiting out the pause.** The browser tests and specs that wait for `location.hash` to change after typing (26 `until(() => location.hash…)` waits across `test/browser` and `e2e` today) read the link through `currentHash()` or the shell's `flushLink` (a helper in `test/browser/helpers.ts`, `link()` or the name that fits, that flushes and returns the hash), or trigger a flush the way a person would (the focus leaving the words); none waits two seconds. A test of the pause itself (below) uses fake timers (`vi.useFakeTimers`) and advances them, never real time. The timed-waits lint (`test/lints.ts`) stays green with no new allowlist entry.
- **The words.** `docs/threat-model.md`'s paragraph "The browser's own history and sync" gains the sentence: the address is written when typing stops for two seconds and whenever the page is hidden or the link is read, so a browser that records each address holds a state per pause and not per keystroke; a password is still the only thing that keeps the content from history. The shell's header comment names the two seconds. `docs/privacy.md` if it describes the address bar; the skill template (`skill/tinyoffice/SKILL.tpl.md`) only if it says when the address changes (`npm run skill` after).

## Measure

In Chromium through Playwright with a persistent context (`chromium.launchPersistentContext`, so the profile's `History` SQLite file is written; read it with the `sqlite3` CLI after the context closes: `SELECT url FROM urls` joined with `visits`), type a paragraph of 200 characters into the Word Processor at 60 ms a key with four natural pauses of three seconds, then leave the page. Count the visits whose address holds the document, on main before the change and on the branch after it. Report both counts. Firefox is not installed here and Safari cannot be driven from this box (Paul tests on an iPhone): say so, and say from the engines' documentation, not from guesses, whether each records a replaced address as a visit; if the documentation does not say, say that.

## Proof

- `test/browser/shell.test.ts` (or where the shell's link is tested), with fake timers: two keys 500 ms apart write the address once, two seconds after the second; a key then the window's blur writes it at once; a key then `visibilitychange` to hidden writes it at once; `currentHash()` after a key returns the typed document without waiting.
- The 26 waits brought to the helper and green, one at a time; `npx vitest run`, `npm run lint`, `npm run build`; the smoke, keyboard and a11y specs on the built site (`PW_PORT=4290`).
- The measurement, with the two counts, in the report.

## Not this

- No change to what the address holds, to `replaceState` rather than `pushState`, to the Back stack, or to the flush points beyond a missing one. No second timer. No change to the library's own keep timing beyond following the flush as it does today.
